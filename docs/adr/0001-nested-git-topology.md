# ADR-0001：外层协作仓 + 内仓生产 monorepo（nested-git 拓扑）

- 状态：已采纳
- 日期：2026-09-08

## 背景

仓库会同时容纳三类内容：调研结果（文献、竞品、领域知识）、外部脚本、真正的生产代码（前端、后端、不分端的核心库、数据库等）。三类内容的受众、变更节奏与 CI 需求差别很大；生产代码本身又会很多。

## 选项

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 外层协作仓 + 一个内仓 monorepo（nested-git） | 前后端接口一起改、一次提交一套 CI；调研材料不污染代码仓；外层小，agent 与新人拉下来只有坐标和文档 | 两层没有 git 级关联，靠 manifest + issue 补位 |
| B. 外层协作仓 + 每端一内仓 | 各端独立 CI 与发版 | 前后端契约变更要跨仓协调，小团队纯属负担 |
| C. 纯 monorepo | 最简单 | PDF、数据集、外部脚本把代码仓撑肥；研究提交与工程提交混一条历史 |

## 决定

采用 A。外层仓只追踪 `repos.json`、`./repos` CLI、文档、调研、外部脚本；`platform/` 是独立 git 仓，被外层 `.gitignore` 整目录挡住。

内仓拆分判据：**运行环境不同、发版节奏不同、维护的人不同，三者占两条才拆。** 最可能先拆出去的是集群执行端，其次是被课题组 notebook 直接安装的核心库。拆仓只需往 `repos.json` 加一段。

## 后果

- 没有跨仓原子提交：跨仓变更以外层仓 issue 为锚，两边 commit 都引用它。
- 工作副本不等于线上：manifest 记 `prod_branch`，`./repos status` 漂移告警。
- 外层零业务代码由 `make hygiene` 机器判定。
