# 愿景与现状

## 目标

为课题组搭建一个科研全自动化平台：把文献调研、假设生成、实验规划与执行、结果分析、论文写作这条链路尽可能交给 AI 与自动化流水线，人聚焦在判断与决策上。

## 给谁用、凭什么（2026-09-16）

**给谁用：非工程师、非本专业的研究者。** 世界不是只由工程师组成的。用户是有一个科研问题、手里有一段能跑的代码和一个数、但不会也不该去学 harness、venv、校验和的人。每一个"要不要做、怎么做"的决定先问一句：一个化学系的博士生用得了吗。

**要解决什么。** 这些人今天已经在用 ChatGPT、Claude Code 调参、重复实验、整表格（学长访谈里"愿意交出去"的那一列，见 [vlm-hard-negatives](cases/vlm-hard-negatives/README.md)）。他们拿到的是一个数：不知道真不真，下周复现不出来，三个月后不知道当时为什么选了这条路。

**凭什么是这个平台，不是直接用 Claude Code。** 产品是两个词，缺一不可：

- **谁都能用。** 研究者跟 agent 聊天，agent 按按钮。命令行是给 agent 的按钮，不是给人的界面。人只在两处出现：发布需求与流程、验收结果（见下一节）。
- **数能拿去用。** 工程师拿到一个数还能自己核，研究者核不了，所以数必须天生可信：写代码的和打分的分开、评分脚本锁死、每轮落盘、新会话不带记忆。这是框架存在的唯一理由，也是它比"直接用 Claude Code"多出来的那一样东西。光降门槛，只是让不可信的结果产得更快。

**哪步复用现成的、哪步自己做，只有一条判据：模型能干的交给模型，模型不能自证的自己做。** 写代码、读文献、起草分析，交给 Claude Code / Codex 这些现成的会话。打分、锁脚本、统计门、记账、隔离环境，必须是零模型调用的死代码（P-1），因为让模型证明自己的数是对的等于没证明。这些死代码封成命令，agent 自由组装（P-12）。

**最终形态。** 研究者跟 agent 聊天：提想法、验假设、查文献、跑实验。agent 按按钮，按钮背后是可信的机器，人在停点上拍板。总目的：降低科研的门槛，且不降低结果的可信度。

**今天离它多远，如实记。** 入口是终端加七步手工，非工程师碰不了。收的形状很窄：几分钟跑完的代码加一个数，学长三个案例只有一个进得来。除了我们没人用过，第一个真任务是我们替学长接的。第一个真用户接入卡在哪，哪就是下一单元。

## 产品形态：两个发布键、一次验收（2026-09-16）

对话是唯一入口，但**流程往下走的钥匙不在 agent 手里，在人手里**。让 agent 判断"需求问清楚了没有"不可靠，所以不让它判断：人不点发布，流程就不动。整条链人出现两次。

**第一步：需求看板，发布即签字。** 人和 agent 聊，agent 把聊出来的东西摆到看板上：目标、数据在哪、算什么指标、**怎么算好**（打分规则的人话版：拿什么数据重算、什么样的产物算废）、一次跑多久、总共花多少钱、要不要能复现。人看着对了，点发布。没发布，后面一个按钮都不许按。裁判脚本在发布**之后**才写：执行层照"怎么算好"写，agent 把脚本和那一栏逐条对，看板上报一句"一致"或"有出入：起点数写死了"。人不读代码。残余风险如实记：这是模型核对模型写的东西，agent 漏了，整个跑就在错的尺子上量；所以"怎么算好"的原文一直跟到结果页，验收时人能对着看。

**第二步：编排看板，agent 摆好、人改。** 发布后 agent 从库里挑一个套餐，或者直接拿单点拼一条流，摆到看板上；默认填好，和需求看板同一页、同一个发布键。一个化学系博士生看到的不是"套餐"和"单点"，是"接任务 → 基线 → 跑 8 轮 → 分析 → 验证"，觉得对就发布；想改的人才展开去拖。这就是低代码平台的真实形态：**不是从零拖，是 agent 摆好、人改**，拖拽的效率比不上让 agent 生成。

**第三步：结果验收。** 跑完 agent 先验收（分析、验证），人和 agent 一起看：改了什么、好了多少、能不能信、复现命令。"怎么算好"的原文并排放着。

**中间不停。** 原来"看基线决定开不开跑"这一停改成机器预检：基线的波动比门槛还大、预算明显不够，框架自动停下来报告，不用人守着（[#42](https://github.com/zephyr4123/TJU-AI4Science/issues/42)）。

**几个词的口径。**

- **单点**：一个按钮。按完就退出，带前置条件（没 run_0 开不了环），不认套餐、不认流程。必停的锁只有一种形状：没有发布记录，按钮不开。
- **套餐**：专家预先定义、预装在库里的一串单点，可以带可选停点；可卸载。agent 从库里挑，不当场发明；但可以不用套餐，直接拼单点。套餐不是穷举出来的，是同一条路被走了两三次之后铺的砖，一个课题组常做的事顶多五到十件。
- **停点**：一个断口 + 一句问话 + 等谁。断口处处都有，因为框架不连跑；用户觉得繁不繁琐只取决于被问几次。钥匙可以提前给：说一句"以后这步不用问我"，锁还在，人不用到场。
- **发布**：就是停点的钥匙，挪到了前面、给了一个按钮。

**为什么这样改。** 原来的三个停点里，"签评分脚本"顺序错了：需求还没确认，脚本先写了，人被叫来签一份还不知道对不对的东西。发布把签字挪到脚本之前，签的是规则不是代码。

## 产品形态补记：两块看板，页面随工作流变（2026-09-17）

上一节的「需求看板 / 编排看板 / 结果验收」三块，在真实协调 agent 拼装并跑通自定义流之后（[#55](https://github.com/zephyr4123/TJU-AI4Science/issues/55)）收成两块，界线用「能写哪儿」划，不用「有没有某个功能」划（[#58](https://github.com/zephyr4123/TJU-AI4Science/issues/58)）：

**编辑台，改「库」。** 可写 `workflows/`（以后加 `capabilities/`）。人和 agent 对话，把能力拼成一条工作流、查通不通、存成文件。它是可选的：预装的两三条流覆盖大多数人，主页面的 agent 发现没有合适的流时说一句「去编辑台拼一条」，不自己偷偷拼。⚠️更正上一节「agent 从库里挑，不当场发明」：在编辑台里 agent 就是拼流的人，#55 证明它拼得出、存得下；主页面才是不发明的那一边。「在编辑台搓能力」是 v2，走代码的路：agent 产出草稿子包与契约测试，落隔离目录，过测试、人合并进 main 才进清单。

**主页面，改「实例」。** 可写当前工作区，只读 `workflows/`。人和 agent 对话，agent 接一条工作流照着跑；跑偏了（半路被杀、自然停、分析要重写）自己按单颗按钮修，但不立新流。需求对齐就在这里，它是 intake 的前三步（人说清、助理整理、人发布），不单独起页：产物是 `requirement.md`，人确认后才开工（2026-09-19 定为唯一内置的门）。对齐那一站给一张对齐清单（四句筛选问题、预算、尽头），随对话从「还没聊」变「填了」，全填钥匙才亮，亮了也是人按；清单读的是 manifest 与 design.md，不是页面自己记的。

**主页面右边那块 = 当前 run 正在照的那条工作流，一步一个模块，按文件顺序排。** 步骤是能力，模块显示这颗能力吐出来的文件——按文件种类通用渲染（JSON 出几个大数字、markdown 出正文、目录出清单、PASS / FAIL 出勾叉），只有账本这种值得一张「每轮一句话」时才配专门视图，新能力没配就走通用（文档即接口在页面上的对应物）；步骤是键，模块就是那颗键；步骤是纯人的事，模块就是一行待办。没拼进流的东西，页面上不存在：装 intake 才有需求对齐，装 quick-look 从 `start` 起、没有需求那块，装一条带写作的流才有写作模块。页面代码是同一份 `steps.map(step => 模块)`，⚠️更正 09-16 页面第一版的三个页签与后来我画的「三站」：那都是把固定流写进页面骨架，与 P-12 相悖。

**做之前要有的：** 工作流步骤带参数（`with: {max_iters: 3}`，按描述符校验；现在「跑 3 轮」写在人话里，第二次跑是 agent 猜的）；run 记下照哪条流、走到第几步、停在等谁（Q-13 说的等待状态，页面读它高亮模块、亮钥匙）；run 开始时快照那条流进 `runs/<id>/`，事后改流不影响跑过的 run；长能力做成异步作业（Q-7），否则真实长度的实验一轮对话等不到。

## 产品形态补记二：工作区与两位助理（2026-09-18）

上一节两块看板的界线是「能写哪儿」，但盘上还没有这条线：任务包、run、对话、作业各自一堆，谁属于谁靠名字猜。主人定两件事（[#70](https://github.com/zephyr4123/TJU-AI4Science/issues/70)）：

**一个工作区 = 一份需求。** 页面顶栏先选工作区，再说话。一个工作区里是这份需求的全部：需求本身、原件、为它取来并改过参数的流、围绕它的对话、七个阶段的产出、后台作业。课题组一个项目有几份需求就开几个工作区。库（能力、工作流、领域包）是全局的，工作区里只有实例。

**主页面的助理只能用流，编辑台另有一位造流的助理。** ⚠️更正上一节「在编辑台里 agent 就是拼流的人」——那句没错，但它和主页面的是**两位**：研究助理对着研究者，取一条流、按需求改参数、照着跑、跑偏了修，不造新流也不造能力，要新流就说「去编辑台拼」；造流助理对着课题组里搭流程的人，看能力清单、拼流、查通不通、存进库，不跑实验、不碰任何工作区。两位各一份指南、各一组可写目录，主页面的对话物理上到不了库。这样切完，页面与权限都只需要认「你在哪个域」。

## 产品形态补记三：需求是根，目录按阶段（2026-09-19）

主人看了工作区的目录：为 auto-research 量身定做，毫无章法，装不下七个阶段；科研是频繁返修、多对多的——实验不止跑一次，数据不只一份，假设也不只一版。从第一性原理重定（[#104](https://github.com/zephyr4123/TJU-AI4Science/issues/104)，纲领 P-19）：

**需求是工作区的根，确认它是唯一内置的门。** `requirement.md` 由助理和人对话攒出来，形式开放——库里放需求模板（通用一份，按学科加），不定死大纲；人在主页面上确认，确认前所有阶段不开工，确认后再改要再确认。端到端全自动的人也得说清要什么、按一次确认，这一下省不掉；别的确认全由流定——放几个断点就确认几次，一个不放就是端到端。

**一个阶段一个目录，每次产出一个子目录，产出之间靠 `from` 引用。** `experiment/2` 读了 `design/1`，`analysis/1` 读了 `experiment/1` 与 `experiment/2`——多对多在盘上是显式的，进度沿引用链算出来。能力是纯函数：显式输入、一个产出目录，不看「最新」；选输入是 agent 看盘决定的事——涌现式的协调，这才是 agent 的意义，卡太死就没意义了。框架只认 `meta.yaml` 一份文件的形状，产出目录里其它一切归产它的那颗能力：换学科就是换一族能力，框架不动。

**主页面**：需求没确认，需求文档就是页面，右边对话，一个动作「确认」；确认了，需求收成顶部一条，流铺开，每个阶段一格、格里列产出与签字。

## 现阶段（0.x 骨架期，2026-09）

已定：

- 仓库拓扑：外层协作仓 + 内仓 `platform/` 生产 monorepo（见 [ADR-0001](adr/0001-nested-git-topology.md)）
- 版本与发布：CHANGELOG 驱动、tag 触发流水线、0.1.0 起步（见 [ADR-0002](adr/0002-versioning-and-release.md)）
- 托管：外仓与内仓都在 GitHub
- 架构（2026-09-10）：协调层（人 + agent）+ 框架 + 执行层 + 工具四层。科研判断归协调层，框架只做机械判定、不连跑不等人；执行层 coding agent 是唯一执行者，裁判上下文隔离；任务与领域是扫目录发现的插件；两层 agent 都集成不手搓、各自可换；能力可自由装配，子集也是流，低代码拖拽出的图是第二种协调层（2026-09-15，P-12）（见 [架构总纲领](architecture/README.md)）
- 协作方式：spec coding + issue driven，先对齐文档再干活，每个工作单元一条 issue
- 定位（2026-09-16，第一个真实输入到达后）：按**工业级开源项目**的标准完善——换一个人、换一个任务，不用问我们，照文档接进来就能跑；第一个真用户接入卡在哪，哪就是产品的洞（用户是谁、凭什么，见上一节）。真任务是检验流程的机会，不是绕过流程的理由：任务自带环境、领域知识有固定的家、接任务有固定流程、每一步机器能查

未定，等它自己长出来：

- 学科适配、验证、评测三层的具体做法（见 [未决项](architecture/open-questions.md)）

两条版本线各走各的（[ADR-0002](adr/0002-versioning-and-release.md)），milestone 与 spec 只用产品版本，且一律带 `platform` 前缀：

|---|---|---|---|

| `platform` | 产品本身，路线图里的初级版、月度正式版 | 0.1.0 骨架 | 0.2.0 初级版 2026-09-28，之后每月 +0.1.0；内测打 `-rc.N` |
