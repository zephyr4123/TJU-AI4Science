## Q-3 验收怎么定义

「验收」有两层：单次运行的验收（这次跑出来的东西能不能信）和版本的验收（这一版做完没有）。

- 单次运行：现在只有零模型的四项检查（`verify`：分析存在、数据表回溯、正文数字在表里、账本对 git）加人在断点上签字。`scoring.yaml` 有 `requirements` 字段（`numeric` / `artifact` / `discussion`，`must_pass`），但还没接判定：唯一的读取点是 id 去重。要定的：`numeric` 与 `artifact` 类由框架确定性判、`discussion` 类交隔离的模型评审（P-2，未实现）——做不做、什么时候做。
- 版本：spec 里的验收命令，尽量一条命令能查。

## Q-4 评测怎么做

评测层评的是框架本身，不是单篇。候选形态：rubric 树（叶子带确定性信号）、组件消融（开关统计门、harness 校验、隔离评审，看结果差多少）、噪声基线（同配置重复 k 次报 σ，任何「改进」先跟 σ 比）。建议先做噪声基线与消融，rubric 树等真任务多了再写。三轮演练的案例卡（`docs/cases/`）是第一批素材。

## Q-7 无人值守时怎么通知人

人在协调层的对话里，框架不等人，作业跑完进那段对话的收件箱、助理接着念——这些都有了。剩下的只有一段通道：人不在时怎么把「轮到你确认了」推给人（现在页面刷新能看到，主动推送没有）。候选：页面通知、邮件、IM。等有人真的挂机过夜再做。

## Q-12 写作能力的形态

论文是长文档、多节、要图、要引用，一次执行层调用写不完。倾向分节多次调用，每节的输入是需求 + 分析产出 + 前面已写的节；模板放领域包；图由 skill 脚本从 `results.json` 与账本确定性生成，执行层只引用不画；写完过数字回溯、引用真伪、图源三条判据（后两条还没实现）。写作阶段的主文件名（`draft.md`）由第一个进来的能力定（P-20）。

## Q-14 加一个能力非得写代码吗

现在必须：步骤子包导出 `run()`。另一条路是声明式能力——目录里只有描述符（YAML）与 `prompt.md`，框架用一段通用驱动起执行层、在产出目录里照说明书干、把结论写回。好处是「新 skill 想当一格」不用工程师；代价是没有代码核对产出，只能靠下游开工时报错与人签字。倾向两种并存：机器能力写代码，模型能力可以只写说明书。主人未拍板。
