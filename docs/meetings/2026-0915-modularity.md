# 2026-09-15 高度模块化对齐

- 参与：主人、Claude
- 起因：主人提出项目要高度模块化：预期需求之一是低代码平台，用户拖拽搭自己的工作流；这只是 UI 形态之一但必须有。端到端的每个模块都要能自由装配、自由装载，不只为 UI，也为扩展。追问：auto-research 只用了七个能力里的两三个，这就是组装的意义？
- 落地：[#33](https://github.com/zephyr4123/TJU-AI4Science/issues/33)，[#34](https://github.com/zephyr4123/TJU-AI4Science/issues/34)

## 结论

1. 认同，且现有架构已在这条路上：P-10 框架不串能力、每条 `ai4sci` 子命令跑一个能力就退出、能力互不 import（`tests/test_layering.py` 机器判）、执行器与算力按名字换。
2. 低代码 UI 不是新一层，是第二种协调层：人 + agent 按步调用能力，静态图按边调用同一批能力，图里还可以放"交给 agent 决定"的节点。写进 README §2 可替换性。
3. "高度模块化"钉成三条可判，写成 P-12：粒度 = 能力不是函数（内环是一个节点带参数）；每个能力有机器可读的描述符；能力对外是一个 Python 函数加磁盘契约，CLI 只是薄壳，协调 agent、UI 后端、测试调同一个函数。
4. 子集流程成立的两个前提：契约挂在产物上不挂在"上游是谁"（实验能力只认过 schema 的任务包，不管谁产的）；子集流程的入口契约由人填。固定流 = 存好的图，不是代码；产物跨流复用。写进 workflow §1"装配与固定流"。
5. 真正的代价不是成本偏大，是过早抽象：现在只有一个真能力，节点框架 / 注册表 / 图 DSL 现在不建。09-22 第二个能力落地时从两个真实例抽出描述符与接口。spec R-5 相应加一句。
6. 图怎么描述、谁解释、与人 + agent 怎么混，开 Q-13。
