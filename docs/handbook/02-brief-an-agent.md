# 02 给 agent 派活怎么写

## 场景

你要让 agent 做一件不小的事：加一层、整理一片文档、跑一轮演练。写得含糊，它会猜；猜错了返工的是你。写得太长，它记不住重点，而且下一个会话又要重写一遍。

## 做法

一份派活（issue 正文、或者一段对话）写四段，顺序固定：

1. **目标**，一句话，说要达成的结果，不说怎么做。「一个没装过任何东西的人照文档 30 分钟内跑到 `ai4sci serve` 起来」比「完善 onboarding」好。
2. **边界**：改哪、不改哪。只改内仓还是两仓都改；能不能动纲领；有没有不许碰的目录。发现边界外的问题怎么办（回来提，不改）。
3. **入口**：从哪个文件读起、最近一张相关的案例卡、对应的纲领条目（P-n）。agent 有了入口就不用全仓扫一遍。
4. **验收**：怎么算做完。最好是机器能查的——一条命令、一个测试名、一个页面截图要出现什么。没有验收的活是没法关的活。

还有几条经验：

- **把用户是谁写进去。** 「不会 ssh 的研究者撞到这里会怎样」这一句改变 agent 修坑的方式：它会修根因而不是绕过去。本仓每个演练都写明研究者是什么水平的人。
- **规矩不放在每次派活里。** 红线、编码标准、commit 写法都在 `CLAUDE.md`，agent 开工自动读到；派活只写这件事特有的。规矩改了改那一份，不用改所有 prompt。
- **说清「不要做什么」和「为什么」。** 「不要为了改而改：结构已经好了，只改内容」这一句让一次文档整理从「重写」变成「对齐」，省了几天。
- **先对齐再动手。** 大活先让 agent 复述它打算怎么做（改哪些文件、分几步、验收是什么），你看一眼再放行。分叉点问一两个高价值的问题就够，不逐节确认。
- **不要求它猜你的口味。** 页面、文案这类主观的东西，先画 ASCII 草图或列几条否决项，再让它做。

## 反例

- 「帮我把这个做好看点」：没有验收，做完你说不好看，它不知道哪里不好看。
- 「帮我修一下」不带复现步骤：它会先花半小时找怎么复现，还可能复现成另一个 bug。
- 一次派十件事：它挑简单的先做，难的写「后续可以……」。一条 issue 一件事。
- 派活里塞整份 CLAUDE.md：每次都塞，改了规矩改十处。

## 本仓真实例子

- 四段的样子：[`docs/meetings/2026-0923-division-of-labor.md`](../meetings/2026-0923-division-of-labor.md) 六个方向每个都是「目标 / 边界 / 入口 / 产出与验收」，会上拍板后按这个拆 issue。
- 一条能直接开干的 issue：[#145](https://github.com/zephyr4123/TJU-AI4Science/issues/145)（本手册）：要做什么、组织方式、章目、素材来源、验收（README 指到它、`make check` 绿、例子里引的 issue 都真实存在）。
- 「用户是谁」改变修法：[#137](https://github.com/zephyr4123/TJU-AI4Science/issues/137) 第三轮演练撞到四个坑，派活时写的是「每个坑当真用户会撞的修根因」，于是 σ 改由框架算而不是让执行层再写一遍 prompt、复现的种子改成照论文而不是加一句提醒。案例卡 [`docs/cases/gua-codex-drill/`](../cases/gua-codex-drill/README.md)。
- 「不要为了改而改」：[#140](https://github.com/zephyr4123/TJU-AI4Science/issues/140) 文档全面对齐代码。派活时先分开「结构」与「内容」两件事，结构保留、只改内容、规矩按仓级 / framework / ui 分层落到各自的 README，不堆成一份大文档。
