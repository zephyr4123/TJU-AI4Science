# 06 摸清现状再动手：大盘点派读者

## 场景

要整理一片东西——几十份文档、一层代码、一个仓的 issue 列表。你和 agent 都不完全知道现状：哪些过时了、哪些互相矛盾、哪些说的功能已经没了。直接开改，改的是想象中的现状。

## 做法

1. **先读，后改。** 读文件、查 git log、跑一遍环境探测、看 issue，基于事实干活。小事自己读；一次读几十份文件的事派读者。
2. **派读者，不派写手。** 把要盘的范围切成几块（按目录、按层），每块一个读者 agent，只读不写，回来交一份结构化清单：每条写「文件:行 / 它现在说什么 / 代码里实际是什么 / 建议」。读者用便宜的模型就够，主线程留给写码的那一个。
3. **读回来的是待核的清单，不是结论。** 逐条核（[04](04-evidence-not-claims.md)），核实的才进 issue。
4. **先分开「结构」与「内容」。** 盘完先问一句：结构（目录、分层、文档体系）本身有没有问题？没有就只改内容——**不要为了改而改**。结构好的东西重排一遍，读它的人要重新学一遍路，agent 的入口也全换了。
5. **一轮探出来的一轮修干净。** 盘点时发现的不对齐、过时、真 bug，只要不是要人拍板的，都在这一轮修，不「另立 issue 下一轮再说」——下一轮永远不来。
6. **派读者也要有边界与产出格式。** 告诉它读哪些目录、不读哪些、回来的清单长什么样；否则回来的是一篇散文。

## 反例

- 读了一个文件就开始改，改完发现另一个文件说的是相反的。
- 「文档太乱了，我重写一遍」——重写的和原来一样乱，只是换了一套乱法，还把别人熟的路都改了。
- 派了五个读者，回来的报告直接照单全改；其中几条是读者把注释当成了行为。
- 盘出三十条问题，修了十条，剩下二十条「记成 issue 以后修」——三个月后那二十条 issue 还在。

## 本仓真实例子

- 一次全量文档盘点 → [#140](https://github.com/zephyr4123/TJU-AI4Science/issues/140)：两仓所有文档切块派读者（只读、便宜的模型），每个读者交「文档说的 vs 代码实际」的清单；回来先核，再决定：结构保留，只改内容；规矩按仓级 / `framework/` / `tests/` / `ui/` 分层落到各自的 README，不堆成一份大文档；主要做减法。同一轮修掉了盘出来的真 bug：助理会话里 `requirement confirm` 与 `sign` 一律拒（只有人能确认）、助理的本子搬出产出 hash、两条永远跳过的测试改对路径、schema 与注释里指向已不存在文件的说法清掉（内仓 CHANGELOG「修复」一节）。
- 盘完才决定「地图」：[#141](https://github.com/zephyr4123/TJU-AI4Science/issues/141) 两仓 README 做成文档索引 + Mermaid 架构图，是盘点之后发现「文档都在、但互相不连」才做的，不是先画图再找内容。
- 派读者的规矩：读者盘出来的东西是「待验证输出」，见 [`CLAUDE.md`「写代码与验收的标准」](../../CLAUDE.md#写代码与验收的标准)「agent 或工具报的 finding 是待验证输出，逐条核实才采信」。
