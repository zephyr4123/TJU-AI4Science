# 07 文档即上下文

## 场景

会话会压缩，长对话会被摘要成几段；聊天记录会丢；换一个 agent、换一台机器，之前聊的全没了。你告诉过 agent 的规矩、决定、坑，下次它一概不知道。

## 做法

1. **写下来的上下文才是 agent 用得上的上下文。** 分四个家，每样东西只有一个家：
   - 规矩 → 两仓 `CLAUDE.md`（agent 开工自动读到；只写纲领性的、通用的，细则按模块放在各层 README）
   - 地图 → 两仓 `README.md`（文档索引、产品与技术架构图、阅读顺序）
   - 过程 → issue 评论（发现、证据、决策，随做随写）
   - 演练 → `docs/cases/` 案例卡（时间线、坑与修法、留着的债）
2. **新会话先读 issue 与文档恢复上下文，不靠记忆。** 派活时给入口（[02](02-brief-an-agent.md)），让它从入口读起。
3. **过期的文档比没有更糟。** 文档说有的功能没了、说的路径不存在，agent 会照着做并且失败得很自信。改代码的同一轮改文档；现实与文档不一致时先改文档再改代码。
4. **一个事实只有一个家，其余地方一句话加链接。** 同一条规矩写三处，改的时候漏两处，三处开始互相矛盾。
5. **内仓与外仓分工**：外层管产品定义、纲领、协作流程、案例；内仓管代码怎么组织、每层的规矩、怎么加东西。问「这个产品是什么」看外层，问「这个函数为什么这样」看内仓。
6. **agent 自己的记忆也当文档管。** Claude Code 有跨会话的记忆文件，里面记的是「定过什么、什么被否决过」；它是补充，不替代 issue——记忆只有那一个 agent 看得到。

## 反例

- 规矩只在聊天里说过：下个会话 agent 又犯，你又说一遍。
- 一份三千行的「总文档」什么都有：没人读完，agent 读到一半上下文就满了。
- README 写了功能列表，六个月没改，一半功能已经改名。
- 决策只在会议上定了，没写进任何地方，两周后没人记得为什么这么定。

## 本仓真实例子

- 会话压缩之后怎么接：本手册写到一半会话被压缩，接上时靠的是记忆文件里的一段（PR 编号、下一步、bash 3.2 的坑）与 issue（[#142](https://github.com/zephyr4123/TJU-AI4Science/issues/142) [#145](https://github.com/zephyr4123/TJU-AI4Science/issues/145)），不靠聊天记录。
- 规矩进 `CLAUDE.md`：[#140](https://github.com/zephyr4123/TJU-AI4Science/issues/140) 把之前只在对话与记忆里的纲领（issue driven、编码标准、验收标准、禁用比喻）写进两仓 `CLAUDE.md`，细则分层落到内仓 `framework/README.md`、`tests/README.md`、`ui/README.md`。
- 地图：[#141](https://github.com/zephyr4123/TJU-AI4Science/issues/141) 两仓 README 的「文档地图」表与三种人的阅读顺序；外层 README「产品一眼看」的 Mermaid 包含关系图（项目 ⊃ 工作区 ⊃ 需求 / 流程实例 / 产出）。
- 案例卡当上下文：[`docs/cases/gua-codex-drill/`](../cases/gua-codex-drill/README.md) 记了「复跑怎么接」，下一轮演练从这一节开始，不用重新摸。
- 文档体系怎么分家：[`docs/architecture/README.md` §6「文档关系」](../architecture/README.md#6-文档关系)。
