1架构与实现现状

系统由四个角色构成：人（研究者 / PI）、助理（协调 agent，一个项目一位）、框架（零模型调用的执行基底）、执行层（写代码的 coding agent 会话）。科研判断归人与助理；框架只做确定性执行与判定；代码仅由执行层产出。

设计原则

工程与验证原则

  • issue driven、spec 先行。每个工作单元对应一条 issue；目标、边界、验收先于实现写清；过程证据（commit、命令输出、数值、文件:行）随做随写入 issue 评论；合并即关闭并附 commit。
  • 机器判据优先。纲领 P-1 至 P-25 每条附可执行的判据；凡能用命令检查的规则进入 make check（分层依赖检查、ruff、pytest、vitest、页面文案词表、CHANGELOG 格式），本地门禁与 CI 完全一致，并由 GitHub ruleset 强制。
  • 行为变更先有失败的测试；集成点必须有测试；不吞异常，验证不过即停（fail-closed，P-7、P-8）。
  • 框架零模型调用，因而可确定性测试；agent 相关行为通过端口的替身实现测试，真实 CLI 仅做门控的冒烟测试。
  • 演练即验收。由 agent 扮演研究者完整走一遍流程；暴露的每个缺陷按根因修复，并沉淀为案例卡与 issue。
  • 未取证不下结论。agent 报告的发现视为待验证输出，逐条核对后方采信。

CLI 是 agent 的第一接口（P-14）

  • 调用方式匹配。LLM agent 以文本调用工具；CLI 文本进出、每个动作一条子命令、结论一行，无需 GUI 自动化，Claude Code 与 Codex 本身即是 CLI。
  • 权限可精确控制。助理面前只有 ai4sci 一个入口，参数走 flag，配置归环境；coding agent 的白名单按命令前缀生效，因此放行范围可精确到子命令。缺少的动作立 issue 增加子命令，不开放裸命令与逃生口。
  • 一份实现，多个调用方。CLI 是能力函数的薄壳；助理、页面后端、测试调用同一个函数（P-12），页面只是同一组端点的客户端。
  • 契约可冻结。子命令、参数、退出码与结论行形状自 1.0.0 起冻结，两家 coding agent 对接的是同一套命令；换底座不改命令。
  • 同一逻辑用于开发过程：GitHub 操作全部通过 gh，agent 可自行开 issue、开 PR、读 CI 日志。

角色划分与能力组合

  • 判断与执行分离。人与助理负责科研判断，框架负责确定性执行与判定，执行层负责产出代码；每个角色可独立测试、独立替换，两层 agent 均走端口与适配器（P-11、P-25）。
  • 能力是模块的粒度（P-12）。每个能力有机器可读的描述符（阶段、职责、边界、输入、产出、终止条件），对外是一个函数与磁盘产物；能力之间的接口是文件而非 schema（P-13）。
  • 小单元组合成强能力。Karpathy 的 autoresearch 在本系统中只是实验阶段的一个步骤 auto-research：与 design、analysis、verify 组合为研究流，reproduction 与 reproducibility 组合为复现流。新能力按同一描述符接入即可参与组合，流程在编辑台装配。
  • 决策不在框架（P-10）。每条命令只运行一个能力，串联由协调层完成；同一能力可复用于多条流程。
  • 状态在磁盘（P-3），契约机器可校验（P-4）。任何会话可被终止并从磁盘续跑；产出被引用或签字后冻结。

issue 是唯一的上下文来源：会话会被压缩，聊天记录不可靠；写入 issue 评论的信息才可跨会话复用。新会话先读 issue 与文档恢复上下文。

人的职责

  • 确定方向、边界与验收标准；对需要决策的事项拍板
  • 扮演研究者进行演练，或作为维护者只修平台、不提供答案
  • review：意图是否正确、抽象是否合理、边界是否完整
  • 确认合并主干、push、历史改写等不可逆操作
  • 对界面、文案与表述给出否决

Claude Code 的职责

  • 摸清现状：读文件、查 git log、探测环境；大范围盘点时派遣只读的读者 agent
  • 实现、测试、运行门禁、开 PR、写 issue 评论、关闭 issue
  • 涉及新工具与版本时使用自带的联网搜索，不凭记忆作答
  • 缺陷先取证再修根因；如实报告失败与跳过
  • 文档与代码同步；一个事实只有一个出处

演练中形成的工程纪律

  • 演练驱动需求。由 agent 扮演不熟悉命令行的研究者完整走一遍流程，暴露的每个缺陷即下一条 issue。
  • 派活时写明用户。「不会 ssh 的研究者遇到此处会如何」决定了修法是修根因而非绕过。
  • 先搜再答。模型知识有截止日期；CLI 参数、库版本、模型价格等一律经自带联网搜索核实并附来源。未放行联网工具时 agent 会以 curl 拼凑，效果差（#114）。
  • 未取证不下结论。agent 报告的发现逐条核对 文件:行 后采信；命令与输出、数值才是证据。
  • 派读者盘点现状，结构合理则只改内容。一次全量文档盘点由只读的读者 agent 完成，逐条核对后在同一轮修完（#140）。
  • 重构要彻底。新路径通过后删除旧入口，文档与测试同一轮跟进，旧数据以一次性脚本迁移，不保留兼容层。
  • 规矩由机器守。能用命令检查的进入 make check；内仓 CI 曾连续三次失败而本地为绿（#144），此后 PR 门禁由 ruleset 强制。

5教程与接手

协作经验整理为十章教程（docs/handbook/），每章四段：场景、做法、反例、本仓真实例子（附 issue、commit、文件:行）。供项目组成员与 agent 阅读。

章要点适用时机
01 issue driven每个工作单元一条 issue，过程写入评论，完成即关闭接手第一件事之前
02 给 agent 派活怎么写目标、边界、入口、验收四段；写明用户是谁首次委派 agent
03 小步快跑与门禁分支内小步提交，make check 与 CI 一致，出分支走 PR修改代码之前

05 先搜再答模型知识有截止日期；新事物经自带联网搜索核实后作答涉及版本、参数、价格、新工具
06 摸清现状再动手大范围盘点派读者；结构合理则只改内容整理文档或代码层
07 文档即上下文issue、README、CLAUDE.md 是 agent 的持久记忆每次新会话

接手路径

  1. 读外层 README.md 的文档地图，再读 CLAUDE.md（规矩）与 CONTRIBUTING.md（流程）。
  2. 承接：
git clone https://github.com/zephyr4123/TJU-AI4Science.git && cd TJU-AI4Science
./repos clone all          # 按 repos.json 将内仓 clone 至 platform/
cd platform && make up     # uv 建 venv、安装依赖、启动 ai4sci serve
  1. 领取 issue（分工定稿后挂在 milestone），从 release/X.Y 切分支，按流程执行。
  2. 受阻时在 issue 中写明现象、已尝试的动作与观察结果。

仅使用平台而不改代码的人无需 clone 外层仓：安装内仓 Release 中的 wheel 即可，见内仓 README「怎么跑 · 只用」。
